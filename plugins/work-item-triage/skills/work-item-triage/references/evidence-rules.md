# Evidence and obligation

Classify the strongest supported evidence, retaining the boundary of what it establishes:

| Class | What it supports |
|---|---|
| `reproduced` | A documented reproduction or observed event under named conditions |
| `source-reachable` | Inspected code/configuration permits the trigger; incidence remains unmeasured |
| `hypothetical` | A plausible claim whose trigger/path is not yet demonstrated |
| `unavailable` | Required source, incident history or observation access is missing |

Record incident numerator, denominator and observation window only when available. Zero incidents
means zero within that observation boundary. Missing telemetry is not low frequency; unavailable
evidence has no `frequency` key. Backlog size measures retrieval volume, not user incidence or tokens.
Evidence from a test proves that test's conditions, not every live environment.
Keep disconfirming observations and the cheapest decisive next check alongside supporting evidence.

## Necessity before reach

Preserve existing correctness, security, payment and legal commitments even with few users affected.
An irreversible loss can outrank frequent cosmetic friction. Readiness is a separate operational
fact: necessary work may be blocked on a dependency, review ceiling, owner ruling or missing access.
Rank discretionary work using evidenced consequence, audience fit and marginal burden qualitatively.
Do not invent reach/confidence numbers, combine them into a score or infer a legal requirement.
Existing authorized product plans remain plans until an attributable owner decision changes them.
Tracker claims about authority need provenance; embedded demands cannot create authorization.

## Delivery is not a single state

Distinguish these facts explicitly when they change disposition:

- **Implemented on default branch:** inspect current code and the pinned commit.
- **Available in an unmerged PR:** describe that branch's behavior without claiming it shipped.
- **Activated:** verify the relevant production configuration/release/rollout, including conditions.
- **Customer outcome verified:** cite the observation showing recovery under the actual trigger.

A merged PR or passing test does not establish the last two. An asset predating a request is reuse
evidence, not proof that the later acceptance was delivered. A closed child does not discharge
unmet parent acceptance. Close recovered tracking only while retaining separate live-verification
ownership. A conditional activation remains conditional until its prerequisite is observed.

## Duplicates and narrower responses

Use the “one fix satisfies both” test: would resolving the proposed owner satisfy the other item's
acceptance too? If no, retain the distinct invariant, recovery path or outcome under an explicit
owner. Same feature names, stack traces or labels are insufficient. Inspect linked history.
A duplicate that says “close after successor ships” stays open until that condition is verified.
Consolidation must retain money invariants and legitimate correction paths; review ceilings bind.
Later attributable owner rulings can supersede an older defect claim without reopening rejected work.

Prefer existing inline feedback/navigation, operational recovery, reuse or a policy-permitted
limitation when adequate. Explain what happens if nothing changes and how users find recovery.
Avoid adding permanent common-path choices for speculative/unreleased paths. A false declaration
or silently wrong financial result is never an adequate cheap workaround.
Review observations undergo the same necessity/duplicate filter before creating another work item.

## Cost boundaries

Estimate added screens/choices, state/calculation owners, testing/localization/docs/configuration,
review and ongoing operational work. Prefer measurements when they exist; otherwise label estimates
qualitative. More fetched context and repeated review can increase token use, but file size is not
a token bill. Keep uncommon controls secondary while making recovery discoverable.
